# 上位机蓝牙连接专项

本文说明产测上位机经 **Dongle 串口** 连接产品蓝牙的完整链路：串口打开时机、固件初始化等待、`扫描连接蓝牙` 测试步骤、以及 `sendCommandWithRetry` 的超时与重发规则。

相关实现与协议细节可对照：

- Dongle AT 层：`agreement/at_protocol/device/dongle/`
- 自由工站步骤执行：`work_station/freework/qfreework_test_case.cpp`
- 串口打开与指令重试：`work_station/test_base.cpp` / `test_base.h`
- Dongle 协议说明：`docs/协议文档/dongle协议.md`

---

## 1. 整体架构

```text
上位机 PC ──USB 串口──► Dongle 模块 ──BLE──► 产品
                │                              │
           AT 文本控制                    产测内层协议
        （扫描/连接/断开）              （qroot / qroot2 / qfctp 等）
                │                              │
           AT+MAC=xx:xx...              PHY 外层帧（通道 1）透传
```

- **蓝牙「连上」**：指 Dongle 与产品建立 BLE 连接，Dongle 上报 `AT+CONNECT_SUCCESS`，上位机 `at->getConnected()` 为真。
- **产测读写 SN/MAC 等**：在 BLE 已连接前提下，经 **PHY 透传** 发 qroot 等内层帧；与 AT 层是两条线，不要混为一谈。

---

## 2. 蓝牙连接在测什么

自由工站里典型步骤 **`扫描连接蓝牙` / `扫描连接蓝牙1`**（ini 配置）：

| 配置项 | 典型值 |
|--------|--------|
| `Channel` | `Dongle` |
| `DeviceCmd` | `BleScanConnect` |
| `Action` | `Set` |
| `Param_string` | `$MAC`（界面 MAC 框 / 流程变量） |
| `WaitReply` | `true` |
| `CommandTimeoutMs` | 统一 **18000**（18 s） |

实际下发（`DongleAtDevice`）：

```text
AT+MAC=AA:BB:CC:DD:EE:FF\r\n
```

连接成功时 Dongle 上报：

```text
AT+CONNECT_SUCCESS\r\n
```

上位机收到后置 `isConnected = true`，日志可见「at蓝牙连接成功」。

断开使用全零 MAC：

```text
AT+MAC=00:00:00:00:00:00\r\n
```

## 3. 串口打开后为什么不能立刻发 AT

Dongle 经 USB 串口打开后，模块固件需要 **短时间初始化**（RTS/DTR 复位、Boot、AT 解析就绪）。若打开后 **立即** 发 `AT+MAC=...`，可能出现：

- 指令被 Dongle 丢弃或无应答；
- 后续产测 PHY 帧异常；
- 表现为「单步扫连失败、偶发连不上」。

因此：**等待应放在「串口打开」这一层，而不是在 qroot/qroot2 等协议层每条指令前加 sleep**——协议层只负责组帧发送，不应感知 Dongle 上电时序。

## 4. 当前代码里的「打开串口后等待」

### 4.1 统一入口（各工站 test_base）

`test_base::openDongleSerialPort()` 在 **打开成功** 后固定等待：

| 常量 | 值 | 行为 |
|------|-----|------|
| `kDongleOpenSettleMs` | **100 ms** | 泵事件循环，不阻塞串口回调 |

日志：`Dongle 串口已打开，等待固件初始化 100ms`

凡继承 `test_base` 的工站（含 **自由工站 QFreeWork**），走 `on_connectButton_clicked()` → `openDongleSerialPort()` 时都会执行。

### 4.2 各场景额外等待（对照）

| 场景 | 打开串口 | 打开后额外等待 | 说明 |
|------|----------|----------------|------|
| 自由工站 **整轮开测** | `beginUiStartTest()` 自动开 | `runTestFlowBootstrap()` 内 **1000 ms** | 开测 bootstrap，再跑第一步 |
| 自由工站 **单步运行** | `runSingleTestCaseStep()` 未开则自动开 | 仅 **100 ms**（`openDongleSerialPort`） | 无 bootstrap 的 1 s；若单步首步即扫连，主要依赖 100 ms |
| 主窗口调试 **点连接** | `MainWindow::openDongleSerialPort()` | `on_connectButton_clicked()` 内 **500 ms** | 与工站 `test_base` 路径不同，调试窗更保守 |
| 主窗口 **MAC 回车连** | 可能触发 `on_connectButton_clicked()` | `waitWork(WAITTIME)`，`WAITTIME` 现为 **0** | 宏在 `my_set/AbIni.h` |
| 步骤 ini `DelayBeforeMs` | — | 按步骤配置（扫连多为 **0**） | 在 `TestCaseRunner::beginStep` 执行，与「刚开串口」无绑定 |

**结论：**

- **整轮开测**且第一步是「扫描连接蓝牙」：一般有 **100 ms + 1000 ms** 量级缓冲，再发 AT。
- **单步运行「扫描连接蓝牙」**且串口是 **当场自动打开**：目前只有 **100 ms**；若仍偶发丢指令，可优先考虑加大 `kDongleOpenSettleMs`，或给扫连步骤 ini 设 `DelayBeforeMs=100`（见 §7），而不是改协议层。

### 4.3 串口打开参数（与复位相关）

工站 `openDongleSerialPort()` 使用 `RtsDtrMode::ToggleReset`，打开时会拉 RTS/DTR，Dongle 会经历硬件复位，**更需要**上述 settle 时间。

## 5. 测试流程里「扫描连接蓝牙」怎么跑

执行路径：`TestCaseRunner::beginStep` → `executeSendCase`（Dongle 分支）。

### 5.1 发指令前

1. 检查 Dongle 串口已打开，否则步骤直接失败。
2. 解析 MAC（`$MAC` / 界面 `macInput` / 成员 `macAddress`）。
3. **清空串口 RX 缓冲**、`at->resetConnected()`，避免沿用上一轮连接态或脏 AT 行。
4. 日志：`发起蓝牙连接：xx:xx:...`

### 5.2 发指令与等待

```cpp
// 超时：max(ini CommandTimeoutMs, 18000)，至少 18 s
sendCommandWithRetry(sendFn, timeoutMs, /* allowResend= */ false);
setCommandWaitSource(CommandWaitSource::DongleAt);
```

- **`allowResend = false`**：窗口内 **只发一次** `AT+MAC=...`，不在超时窗口内重复发 AT（避免打断 Dongle 扫描/连接状态机）。
- **`needAsyncDone = true`**（扫连/直连步骤）：步骤是否通过，主要看 **`at->getConnected()`** 变为真（或收到 `AT+CONNECT_SUCCESS` 结束 `sendCommandWithRetry`），而不是「发完 AT 即过步」。

### 5.3 步骤结束条件

在 `tickOrderedTestStepLoop` 中：

- `dongleBleConnect && at->getConnected()` → `stepRuntime_.done = true`，`testData = "已连接"`。

若超时仍未连接：`sendCommandWithRetry` 失败，步骤判失败。

### 5.4 后续产品协议步骤

`stepRequiresProductBle` 为真的步骤（Product 通道 Get/Set 等）要求 **已连接**。若未连接且当前步不是扫连， `startTask` 会周期日志提示，并在未禁止重连时尝试再次 `BleScanConnect`（辅助逻辑，不能替代流程里的显式扫连步）。

## 6. 为什么不在协议层（qroot2 等）每条指令加延时

| 层级 | 职责 | 是否应加「开串口后延时」 |
|------|------|--------------------------|
| `test_base::openDongleSerialPort` | 硬件串口生命周期 | **是**（已实现 100 ms） |
| `test_case` Timing / Hook | 步骤级时序 | 按需（`DelayBeforeMs`） |
| `Qroot2::sendPacket` / `DongleAtDevice::sendAtLine` | 组帧/发 AT | **否**（无「是否刚开串口」上下文，且会拖慢所有已稳定连接后的指令） |

产测内层（qroot）走 **PHY 通道 1**，前提是 **BLE 已连接**；此时瓶颈在连接与通道，不在「每条 qroot 前 sleep」。

## 7. `sendCommandWithRetry`：超时与重发（含 18 s 不重发 3 次）

### 7.1 语义

- 第二参数 **`timeoutMs`** = 本步 **总等待时间**（不是「单次应答超时」）。
- 第三参数 **`allowResend`**：
  - `true`（默认）：在总窗口内按间隔 **重复发送同一条指令**；
  - `false`：**只发 1 次**，等到总超时截止。

### 7.2 普通指令（`allowResend = true`）

- 重发间隔 ≈ `totalMs / 3`，限制在 **200 ms～2000 ms**。
- 例：`CommandTimeoutMs=3000` → 约每 1 s 重发，总窗口 3 s 内可发多次。
- 超时日志：`指令超时未响应（已等待3000ms，共重发N次）`，N = 发送次数 − 1。

### 7.3 蓝牙连接类（`allowResend = false`）——**故意不重发**

扫连 / 直连 / 按名连 / OTA / App / Main 等（`isDongleBleConnectCmd`）一律：

```cpp
sendCommandWithRetry(sendFn, timeoutMs, false);
```

此时：

- 间隔 = **整个 timeoutMs**（定时器只在窗口 **末尾** 触发一次超时检查）。
- **实际只发 1 次** `AT+MAC`（或 `AT+DCON` 等）。
- 超时日志里 **`共重发0次`** 是预期行为，不是 bug。

因此：**ini 里设 `CommandTimeoutMs=18000`，并不是「18 秒内重试 3 次」**，而是 **「只发一次 AT，最多等 18 秒看是否连上」**。

设计原因（代码注释）：连接过程中重复发 `AT+MAC` / `AT+DCON` 会 **打断 Dongle 内部连接流程**，反而更容易失败。

### 7.4 与 `needAsyncDone` 的区别（勿混淆）

| 概念 | 含义 |
|------|------|
| `allowResend` | `sendCommandWithRetry` 是否在超时窗口内 **重复发同一条 AT/协议指令** |
| `needAsyncDone` | 流程是否必须等 **步骤异步结案**（如连上 BLE、Gate 上报、Hook 采样结束）才能进入下一步 |

扫连步骤两者均为「是」，但含义不同。

## 8. 蓝牙连接超时配置（统一 18 秒）

| 步骤类型 | `CommandTimeoutMs` | 实际等待 |
|----------|-------------------|----------|
| `扫描连接蓝牙` / `扫描连接蓝牙1` / `直连接蓝牙` 等 | **18000** | **18 s** |
| ini 未配置 | runner 默认 **18000** | **18 s** |

代码位置：`qfreework_test_case.cpp` 中 `timeoutMs = qMax(timeoutMs > 0 ? timeoutMs : 18000, 18000)`，**下限 18 s**；ini 与默认值均已统一为 18000。

## 9. 推荐配置与排查

### 9.1 扫连仍偶发失败

1. 确认日志里 **AT TX** 出现在「Dongle 串口已打开，等待固件初始化 100ms」**之后**。
2. **单步扫连**且刚自动开串口：若 100 ms 不够，可：
   - 适当增大 `test_base.h` 中 `kDongleOpenSettleMs`（需改代码编译），或
   - 步骤 ini 增加 `DelayBeforeMs=100`～`200`（仅该步生效）。
3. 确认 MAC 有效、产品可广播、Dongle 天线正常。
4. 看是否收到 `AT+CONNECT_SUCCESS`；有 SUCCESS 但步骤不过，查 `getConnected` / 步骤名是否被识别为扫连步。

### 9.2 误以为「18 s 应重发 3 次」

- 扫连类步骤 **设计上不重发**；当前统一 **18 s** 总等待，**不是**在 18 s 内自动重发 3 次 AT。
- 若需「连不上再整步重跑」，用流程 **重试步骤 / 重新开测**，而不是在 `sendCommandWithRetry` 里对 `AT+MAC` 连发。

### 9.3 连接成功后产测指令失败

- 与 **AT 扫连** 无关时，查 **qroot 协议、PHY 封包、产品工厂模式** 等。
- 串口 settle 只解决 **Dongle AT 就绪**；BLE 连接成功后内层协议另有超时（Product 通道 `sendCommandWithRetry` 默认 `allowResend=true`）。

## 11. 小结

1. **蓝牙连接** = Dongle AT 层 `AT+MAC` + 等待 `AT+CONNECT_SUCCESS`，与 qroot 产测帧是先后关系。
2. **串口打开后必须留固件初始化时间**；统一在 `openDongleSerialPort` **100 ms**，整轮开测另有 **1 s** bootstrap；**不应**在 qroot2 每条指令前加延时。
3. **扫连步骤**在代码里 **只发一次 AT**（`allowResend=false`），`CommandTimeoutMs=18000` 表示 **最长等 18 秒**，**不是** 18 秒内重发 3 次。
4. 单步扫连若仍紧，可加大 settle 或步骤 `DelayBeforeMs`，优先改 **串口/步骤时序**，不要改协议层发帧逻辑。
